# Celebration & Event Planner SaaS — Original Product Specification

## Product definition

Build a **Celebration and Event Planner SaaS** that helps a defined user persona plan and execute an event within their budget, preferences, timeline, and constraints. Important point to note is the goal is not an AI that merely suggests party ideas, but an AI that helps users **actually make the event happen**.

The target user is intentionally open-ended: it may be an individual/family organizer, community organizer, or event-management company, but the submission must solve a genuine problem this persona.

The SaaS should help users manage the connected moving parts of event planning: budget, guest list, venue, decoration, food, vendors, timeline, dependencies, and last-minute changes.

## Product principles

These are the practices the hosts repeatedly emphasized:

- Solve one real planning problem for one defined user, rather than building every possible feature.
- Treat event planning as a connected system: guest count, menu, decoration, budget, vendors, and timeline affect one another.
- Use GenAI where it adds meaningful value: understanding needs, personalizing suggestions, adapting to changes, and converting natural language into actionable plans.
- Keep the user in control; AI should ask, listen, and adapt—not assume what the user wants.
- Be transparent about estimates, assumptions, and unverified vendor information.
- Avoid adding features merely because they sound impressive.
- Design for change: a revised budget, earlier event date, changed guest count, or vendor cancellation must update the plan rather than force the user to start over.
- Focus on execution support—budgets, deadlines, dependencies, coordination, and changing requirements—not inspiration alone.

## Core user journey

The SaaS should follow this flow:

1. User selects or describes the event type and context.  
2. System asks practical onboarding questions.  
3. System generates a personalized starting plan.  
4. User refines priorities, budget, guests, theme, and requirements.  
5. System maintains a task timeline with dependencies and deadlines.  
6. User records vendor quotations and compares options.  
7. When constraints change, the system revises the plan and highlights affected decisions.

## Functional acceptance criteria

### Event creation and onboarding

| ID | Acceptance criterion |
|---|---|
| EM-01 | The system must allow a user to create an event by entering the occasion, event date, budget, expected guest count, and event duration or planning window. |
| EM-02 | Before generating a full plan, the system must ask practical clarifying questions such as occasion, budget, expected attendees, event date, desired experience level, spending priorities, and absolute must-haves. |
| EM-03 | The system must generate an initial event plan based on the user’s actual inputs, not a generic template. |
| EM-04 | The system must support multiple event types, including birthday parties, weddings, 50th-birthday celebrations, and community gatherings. |
| EM-05 | The system must allow the user to choose a specific persona or use case, such as a tight-budget small celebration, wedding task planning, or community-event coordination. |
| EM-06 | The system must clearly present the generated plan as a starting point that the user can refine. |

### Personalized planning

| ID | Acceptance criterion |
|---|---|
| EM-07 | The system must personalize recommendations using user-provided preferences such as atmosphere, guest age groups, interests, cultural preferences, accessibility needs, and venue limitations. |
| EM-08 | The system must allow the user to refine AI-generated concepts through follow-up conversation. |
| EM-09 | When a user says a suggestion is too expensive or unsuitable, the system must propose relevant alternatives. |
| EM-10 | The system must adapt recommendations for mixed audiences, such as events suitable for both children and elderly family members. |
| EM-11 | The system must not assume user preferences; it must ask, listen, and adapt based on user responses. |
| EM-12 | The system must recognize that two users planning the same event type may require materially different plans. |

### Budget management

| ID | Acceptance criterion |
|---|---|
| EM-13 | The system must allow users to organize major expenses into categories such as venue, catering, decoration, photography, and other event-related costs. |
| EM-14 | The system must help users create an initial budget allocation across those categories. |
| EM-15 | The system must allow users to compare planning scenarios. |
| EM-16 | When the user increases allocation to one category, such as photography, the system must show the effect on the remaining budget. |
| EM-17 | When guest count increases, the system must identify affected costs and potential compromises. |
| EM-18 | When expected expenses exceed the budget, the system must present trade-offs and let the user choose what matters most, rather than automatically cutting costs across the board. |
| EM-19 | The system must clearly label AI-generated or assumption-based costs as estimates, not confirmed vendor prices. |
| EM-20 | The system must not present invented prices as confirmed costs. |

### Timeline and task execution

| ID | Acceptance criterion |
|---|---|
| EM-21 | The system must convert a vague request such as “help me organize my wedding” into a structured sequence of tasks. |
| EM-22 | The system must organize tasks by priority and deadline instead of presenting unrelated checklist items. |
| EM-23 | The system must identify dependencies between tasks; for example, venue and date decisions should precede several downstream arrangements. |
| EM-24 | When a user marks a task complete, the system must update the event plan. |
| EM-25 | When a task is delayed, such as a venue booking, the system must identify other tasks that may need attention. |
| EM-26 | The system must show the user what needs to be done next, moving them from “I have an event coming up” to an actionable execution plan. |
| EM-27 | The system must allow the user to revise the plan when constraints change, such as a reduced budget or an event date moved two weeks earlier. |
| EM-28 | After a constraint changes, the system must update the affected budget, timeline, dependencies, and recommendations without requiring the user to restart from scratch. |

### Vendor coordination

| ID | Acceptance criterion |
|---|---|
| EM-29 | The system must help users define what they need from each vendor, such as caterer, photographer, decorator, or venue provider. |
| EM-30 | The system must help users prepare relevant questions to ask each vendor. |
| EM-31 | The system must allow users to record vendor quotations. |
| EM-32 | The system must compare quotations against the user’s budget and requirements. |
| EM-33 | The quotation comparison must show what is included, how many guests are covered, additional charges, and items that still require clarification before booking. |
| EM-34 | If the system provides vendor recommendations or availability, it must clearly indicate that the information requires verification. |
| EM-35 | The system must not claim a vendor is available or that a price is confirmed unless that information has been verified. |
| EM-36 | The system must act as a coordination layer between the user and vendors, not claim that AI can automatically arrange everything. |

## GenAI requirements

The hosts stressed genuine, useful GenAI adoption—not superficial AI usage.

| ID | Acceptance criterion |
|---|---|
| AI-01 | The application must use GenAI to understand the user’s situation, priorities, and constraints before producing recommendations. |
| AI-02 | The application must use GenAI to personalize suggestions rather than return static event-planning templates. |
| AI-03 | The application must use GenAI to adapt the plan when user inputs or constraints change. |
| AI-04 | The application must use GenAI to convert natural-language requests into actionable plans. |
| AI-05 | The application must respond to the user’s actual inputs in real time; it must not rely on hardcoded or dummy data for GenAI-driven flows. |
| AI-06 | If a user enters an 8 lakh budget, the generated recommendations and allocations must be appropriate for an 8 lakh budget. |
| AI-07 | Dummy data may be used only for ML/model-training scenarios, not as the basis for real user-facing GenAI answers. |
| AI-08 | The application must be transparent about AI limitations, assumptions, estimates, and unverified information. |
| AI-09 | The application must keep the user in control of final decisions. |
| AI-10 | The application must avoid using AI where it does not solve a meaningful user problem. |

## MVP scope recommendation

Start small, the strongest MVP would focus on **one persona and one execution problem**, rather than building a full marketplace, invitation system, guest manager, reminder engine, and theme generator at once.

A strong MVP could be:

- **Persona:** A family planning a wedding or small celebration with a fixed budget.  
- **Core problem:** Turning an initial event idea into a realistic, revisable execution plan.  
- **Must-have modules:** Onboarding questions, personalized plan, categorized budget, scenario comparison, prioritized task timeline with dependencies, plan revision on constraint change, and vendor-quotation comparison.  
- **AI role:** Clarify needs, personalize recommendations, explain trade-offs, adapt the plan, and convert natural-language requests into tasks.  
- **Explicit non-goals for MVP:** Live vendor marketplace, real-time vendor availability, confirmed pricing, invitations, reminders, and guest RSVP management—unless they directly serve the selected persona’s core problem.

## Final acceptance test

The decisive product test from the session is:

> A user creates an event, receives a budget and timeline, then returns with changed constraints—such as a lower budget and an event date moved earlier. The application must help them revise the plan; it must not force them to begin again.

In one line: **build an execution-oriented, transparent, personalized event-planning SaaS—not an AI idea generator.**
