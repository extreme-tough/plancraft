## How to read this spec

**Tiers**

- **MUST**: needed for the core loop (*create event → generate plan → edit budget/tasks → revise on constraint change → compare vendor quotes*) or for one of the six scoring categories. Without it, we don't ship.
- **SHOULD**: build only after every MUST is built **and tested**, in the order given in §11.
- **LATER**: not in this submission. The repo must not contain half-built versions of these.
- **Principle**: guidance that isn't testable on its own. It is covered through other requirements.

**How each requirement is verified**

| Code | Meaning |
|---|---|
| U | Unit test |
| P | Property-based test (fast-check or equivalent) |
| S | Contract test on an AI input or output schema, using fixtures that include malformed cases |
| E | Playwright end-to-end test. The server runs with a fixture AI provider and the Firebase emulators (test environment only, see AI-05 and EM-59) |
| A | Automated accessibility check (axe) |
| D | A manual demo of 30 seconds or less against the live AI. The scripts are in §13 |
| R | A check on the repo, README or CI |

Automated tests never call the live model. Fixtures live only under `tests/`, which AI-07 allows because they are test data, not answers shown to users.

## 1. Product definition

Build a **Celebration and Event Planner SaaS** that helps people plan and carry out an event within their budget, preferences, timeline and constraints. The goal is not an AI that suggests party ideas. The goal is an AI that helps users **actually make the event happen**.

The product serves anyone organizing a celebration, anywhere in the world:

- individuals and families
- community organizers
- event professionals running several events

They all use **one planning engine**: event → budget lines → tasks with dependencies → vendor quotes → revisions. What the user selects (EM-05) changes the onboarding questions, the default budget categories and the starting tasks. It does not change the engine. The AI personalizes each plan from the user's own inputs, so two users with the same persona still get different plans (EM-12).

**(edited v3)** The engine is generic, but tuning, test fixtures, the demo and the video use **one** persona (A23). Breadth is something the engine allows, not something the demo tries to show.

The product manages the connected parts of event planning: budget, guest numbers, venue, decoration, food, vendors, timeline, dependencies and last-minute changes.

## 2. Product principles

These are unchanged from v1:

- Solve real planning problems for clearly defined users, rather than building every possible feature. *(v2 reading: each supported use case must be deep, not shallow. The point is depth, not a limit on who the product serves.)*
- Treat event planning as a connected system: guest count, menu, decoration, budget, vendors and timeline affect one another.
- Use GenAI where it adds real value: understanding needs, personalizing suggestions, adapting to changes, and turning natural language into actionable plans.
- Keep the user in control. The AI should ask, listen and adapt, not assume what the user wants.
- Be open about estimates, assumptions and unverified vendor information.
- Avoid adding features just because they sound impressive.
- Design for change. A revised budget, an earlier date, a changed guest count or a vendor cancellation must update the plan, not force the user to start over.
- Focus on getting the event done (budgets, deadlines, dependencies, coordination, changing requirements), not on inspiration alone.

## 3. Target users and use cases

| Use case (EM-05 selector) | Typical user | What changes in the starting plan |
|---|---|---|
| Tight-budget small celebration | Individual or family: birthday, anniversary, milestone birthday | Fewer categories. Emphasis on trade-offs and doing things yourself. Short planning window |
| Wedding planning | Couple and family | Many vendors. Events with several parts. Long dependency chains |
| Community event coordination | Community or society organizer | Budget pooled from contributions. Permits and logistics tasks. Large, uncertain turnout |

**(edited v3)** "Multiple events" is no longer a use case. An event professional uses any of the three use cases and keeps several events (EM-40, SHOULD). There is no client management or billing.

**Global scope:** Users in any country. Each event has **one currency**, chosen when the event is created. Amounts are formatted for the user's locale. Cost estimates take into account the event's location.

**(new v3, updated after Q3) Accounts.** Real users sign in with Google. Reviewers who open the URL without signing in are signed in automatically to **one shared demo account** holding the demo persona's data, reset every night (EM-58, EM-63). Each Google user's events are stored in Cloud Firestore and are visible only to that user (EM-59). Apart from the shared demo account, there is no sharing between users in the MVP.

**Interface language:** English only. Numbers, currency and dates are formatted for the user's locale (Q10).

## 5. Core user journey

0. **(new after Q3)** The user signs in with Google, or, without signing in, lands in the shared demo account, which already holds the demo persona's event.
1. The user picks a use case and describes the event: type, location, date, budget and currency, guest count, and any extra parts (for example, a dinner the night before). **(edited v3)**
2. The system shows a short, fixed set of practical questions for that use case. **(edited v3)**
3. The system generates a personalized starting plan: budget lines, tasks with dependencies and deadlines, and what to ask each vendor.
4. The user edits lines and tasks directly, or types a change request in plain language. **(edited v3)**
5. The system keeps a task timeline with dependencies and deadlines.
6. The user pastes vendor quotes (or, if built, uploads `.docx`) and compares them per budget line. **(edited v3)**
7. When constraints change, the system shows a **before/after view** of the affected budget lines, tasks and quotes. The user **applies or discards** it.

### 7.2 Rules common to every call (new v3)

1. **Path:** browser → the app's server (Cloud Run) → Gemini on Vertex AI. The server authenticates to Vertex AI with its Cloud Run service account (role `Vertex AI User`), so **no AI API key exists** anywhere (ENG-02, ENG-08).
   **Caller identity (new after Q3):** every `/api/ai/*` request carries a Firebase ID token (`Authorization: Bearer …`). The shared demo account has one too, from its custom-token sign-in. The server verifies the token with the Firebase Admin SDK, and a missing or invalid token returns `401 UNAUTHENTICATED`. Rate limits count per user ID for Google users, and **per IP address for the shared demo account** (ENG-08). For revisions, the server reads the plan from that user's Firestore data, so a user can't send another user's event ID.
2. **Request check:** the server validates the request against its schema. If it fails, the response is `400 INVALID_REQUEST` and the model is not called.
3. **Structured output:** the model is called in JSON mode with the response schema, where the provider supports it. **Provider enforcement isn't trusted.** The server validates the full schema and the rules again. Schemas avoid `oneOf` and `$ref` in what is sent to the provider (flat objects, nullable fields) so they work with Gemini's response-schema subset. The full JSON Schemas below are the server-side source of truth.
4. **Money in AI inputs and outputs** is a JSON number in **major units of the event currency** (for example `800000` for ₹8 lakh). Code converts it to integer minor units using the currency's exponent, rounding half up. Non-finite values, negative values (except discounts) and values above 10¹¹ are rejected.
5. **References:** before sending, the server replaces internal UUIDs with short references (`L1`…, `T1`…). New items the AI creates use `N1`…. Keys are mapped back after validation. This saves tokens and stops the model inventing IDs.
6. **Text:** trimmed, control characters removed, maximum lengths enforced, and always **rendered as text, never as HTML**.
7. **Untrusted text:** quote text and free-text requests are placed in delimited blocks (`<quote>…</quote>`), and the system prompt says to treat them as data. The output schemas **can't express** a change to event constraints or to locked lines, so an injected instruction can at worst produce wrong extracted fields, which are labelled unverified and checked by EM-49.
8. **Pipeline:** request schema → prompt → model (timeout) → `JSON.parse` → output schema → rules → success. If parsing, the schema or a rule fails, the server makes **one automatic repair attempt**, sending the same prompt plus the list of failed rule IDs. If that also fails, it returns an error. Timeouts are not retried automatically. At most two model calls per user action.
9. **Response envelope:**

   ```json
   { "ok": true,  "data": { }, "meta": { "attempts": 1, "model": "<model id>" } }
   { "ok": false, "error": { "code": "AI_INVALID_OUTPUT", "message": "…", "retryable": true } }
   ```

   | Code | HTTP | Retryable |
   |---|---|---|
   | `INVALID_REQUEST` | 400 | no |
   | `RATE_LIMITED` | 429 (with `Retry-After`) | yes, after the wait |
   | `AI_UNAVAILABLE` | 503 | yes |
   | `AI_TIMEOUT` | 504 | yes |
   | `AI_INVALID_OUTPUT` | 502 | yes |
   | `AI_BLOCKED` (provider safety block) | 502 | no |
   | `UNAUTHENTICATED` | 401 | no (the app signs in again, then retries once) |
   | `DAILY_LIMIT_REACHED` | 429 | no, until midnight IST |

10. **Limits:** timeouts are 45 s for the plan call and 30 s for the other two. Request bodies are capped at 100 KB. Each call has its own maximum output tokens. Rate limits are in ENG-08.
11. **Logging:** the call, error code, number of attempts and failed rule IDs are logged. **User text and AI text are never logged.**

## 8. Architecture principles

### 8.1 Who does what

| GenAI does | Code does |
|---|---|
| Understanding the event description and free-text requests | All money arithmetic: totals, remaining budget, per-guest amounts, rounding, in integer minor units |
| Proposing categories, lines, weights, tasks, lead times, durations and dependencies for the use case and location | Turning weights into amounts that add up exactly (EM-14) |
| Estimating cost ranges for the location and currency, with stated assumptions | Calculating deadlines and statuses, checking for dependency loops |
| Proposing trade-off options as typed operations | Recalculating for budget, date and guest changes, building before/after differences, enforcing Apply and Discard, protecting `Confirmed` lines |
| Pulling structured fields out of quote text | Quote totals, currency and tax checks, grounding checks |
| Explaining trade-offs | Checking every AI output against its schema and rules |

**Rule:** the AI returns structured **proposals**. Code checks them and calculates the result. The user approves. The AI never writes final amounts, totals, dates or labels into the plan.

**(new v3) Domain module:** money, allocation, guest pricing, deadlines, graph checks, quote checks, the diff builder and apply/discard live in one pure module with no UI, storage or network imports. Every invariant in ENG-07 is tested against this module.

### 8.2 Where cost estimates come from

The AI estimates costs from the user's inputs: location, currency, guest count, budget level and use case. Each estimate is a range with its assumptions stated, and is labelled `AI Estimate` (EM-41). **(edited v3)** The range is shown next to the line's allocated amount and drives the "Under-funded" flag. It never replaces the allocation (A5). There is no built-in price table, which keeps the product global and avoids AI-07's ban on dummy data. Users replace estimates with quotes as they collect them.

### 8.3 Where task lead times come from

**(edited v3)** The AI proposes each task's lead time, duration and dependencies for the use case. The schema enforces the ranges (lead time 0–540 days, duration 1–90 days), and values outside them are rejected rather than clamped. Code rejects loops and calculates the deadlines (EM-46).

### 8.4 Reading quote files

**(edited v3)** In the MVP, quotes are pasted as text. `.docx` (SHOULD) is read in the browser with mammoth `extractRawText`, loaded only when needed. Text PDFs with pdfjs-dist are LATER. Only the extracted text goes to the server and then to the AI. The scanned-file check (EM-48) and the line-item total check (EM-49) run in code.

```ts
  name: string | null;                    // scenarios only
  baseVersion: number;                    // EM-56
  changes: { field: 'budget' | 'date' | 'guests'; before: string; after: string }[];
  requestText: string | null;
  deterministicOps: Op[];                 // calculated by code
  ai: RevisionResponse | null;            // validated, refs mapped to IDs
  selectedOption: 'O1' | 'O2' | 'O3' | null;
}
```

**Calculated, never stored:** remaining, percentages, deadlines, latest starts, statuses, flags, quote totals and checks, "Next up". Applied or discarded proposals are deleted. Undo history is LATER.

**Where it's stored (new after Q3):** `EventPlan` without `quotes` is one Firestore document at `users/{uid}/events/{eventId}`, comfortably under Firestore's 1 MiB document limit. Each `Quote` is its own document at `users/{uid}/events/{eventId}/quotes/{quoteId}`, because raw quote text (up to 20,000 characters each) would push the event document toward that limit.

### 8.6 Revisions and scenarios (new v3)

Both are a `Proposal`. They differ only in how they start, how many can exist and how they end.

| | Revision (MUST) | Scenario (SHOULD) |
|---|---|---|
| Started by | The EM-27 form, the "Ask for a change" box, or "Vendor cancelled" | A "What if…" button |
| Constraint values | Become the event's real values on Apply | Hypothetical. The event never changes |
| How many | At most 1 pending | Up to 3, each named |
| Survives a reload | Yes | Yes |
| How it ends | **Apply** (the plan changes and `version` goes up by one) or **Discard** (deleted) | **Delete**, or **Use this**, which turns it into the pending revision, recalculated against the current `version` |
| Screen | The before/after screen (UX-08) | A Scenarios tab with columns Current / A / B / C: total, shortfall, at-risk tasks, lines changed |
| When the plan changes underneath it | EM-56 blocks Apply until it is recalculated | Recalculated by code whenever it is opened. AI options are fetched again only when the user asks |

Operations generated by code for constraint changes: `set_event_budget`, `set_event_date` and `set_event_guests`, plus the per-guest line recalculations that follow from them. These event-level operations exist **only** in `deterministicOps`. The AI operation schema can't express them.

### 8.7 Accounts, storage and hosting (new after Q3)

```
Browser (Next.js on Firebase App Hosting, which runs on Cloud Run)   (build)
 ├─ Firebase Auth ── Google sign-in (EM-57) or custom token for the shared demo account (EM-58)
 ├─ Firestore (client SDK, offline cache, onSnapshot) ── users/{uid}/events/** guarded by rules (EM-59)
 ├─ Cloud Storage ── users/{uid}/events/{eventId}/moodboard/** guarded by rules (EM-67)
 ├─ /api/demo/session ── same-origin route ── mints a custom token for uid "demo-shared"
 └─ /api/ai/* ──────── same-origin route
                                            ├─ verifies the Firebase ID token (Admin SDK)
                                            ├─ checks and counts usage in /usage/** (Admin SDK only)
                                            ├─ reads the user's plan for revisions (Admin SDK, same uid)
                                            └─ Gemini on Vertex AI (service account, no key)

Cloud Scheduler (3:00 AM IST) ──> POST /api/internal/demo-reset, OIDC-verified (EM-63)
                                   ├─ wipes users/demo-shared/events/**
                                   ├─ writes the seed inputs + sample quotes
                                   └─ generates the plan with live Gemini, validated as in §7.3
```

- **The browser writes the user's own data directly** through the Firestore client SDK, guarded by the rules, with version-checked transactions (EM-62). The API server never writes users' event data. It reads a user's plan for revision requests and keeps the usage counters. Only the reset route writes demo data on the server side.
- **The domain module stays pure** (§8.1). Storage sits behind a small repository interface with two implementations: in-memory for unit and property tests, and Firestore for the app and E2E (against the emulator).
- **The shared demo login (EM-58):** `POST /api/demo/session` takes no input and returns a custom token for the fixed user ID `demo-shared`, created with the Admin SDK. The App Hosting service account needs the `Service Account Token Creator` role on itself to sign tokens. The endpoint is rate-limited to 20 requests a minute per IP, and it is the **only** way to obtain that user ID. Nothing ever links that account to another sign-in method (EM-60).
- **Demo seed (EM-63):** the seed lives in `src/demo/seed.ts` as **inputs only**, and a unit test asserts it contains no lines and no tasks (A27). The reset route and the "Try an example" button both use it.
- **Rate limits and the daily cap** (ENG-08, Q5) use Firestore counter documents under `/usage/{yyyy-mm-dd IST}/…`, updated in transactions by the server. These work across Cloud Run instances, unlike in-memory counters. The day rolls over at midnight IST.
- **Auth settings:** only the Google provider is enabled. Anonymous sign-in stays **disabled**, and the demo account signs in through custom tokens. Authorized domains are only the Hosting domain(s) and `localhost`. The Firebase web config is public by design and is not a secret, but its API key is restricted in Google Cloud to the Hosting domains and the Firebase APIs.

**ENG-07 testing**

- **Property tests** on the domain module:
  - **INV-1:** Σ line amounts + remaining = budget, in integer minor units, after any sequence of operations.
  - **INV-2:** `Confirmed` lines are unchanged by any proposal apply, AI option or recalculation.
  - **INV-3:** the dependency graph has no loops after any accepted edit or operation.
  - **INV-4:** after Discard, the stored plan is identical to its state before the proposal.

  - **INV-8:** parse(format(x)) = x for the `en-IN`, `en-US`, `de-DE` and `ja-JP` locales.

  - At least one valid fixture.

**ENG-08 security**

- **No AI key exists.** Vertex AI is reached with the Cloud Run service account, which has only the roles it needs: `Vertex AI User`, plus Firestore access for the usage counters and for reading plans.
- **Authentication:** every `/api/ai/*` request needs a valid Firebase ID token, verified on the server (§7.2). Firestore access is governed by the EM-59 rules, which deny by default.
- The server checks every request against its schema, and every AI output against its schema and rules (§7).
- Limits:
  - Request bodies are capped at 100 KB, quote text at 20,000 characters, and import files at 2 MB.
  - Each Google user ID is limited to 10 AI requests a minute and 100 a day.
  - The shared demo account is limited **per IP address** to 10 AI requests a minute and 50 a day, and to **1,500 a day in total**, so the demo can't use up the whole daily cap meant for real users as well. The IP is taken from the forwarding-header entry that Google's infrastructure adds (the exact header for a Hosting → Cloud Run rewrite is confirmed during the build, with a test), never from a value the browser controls.
  - All users together are limited to **2,000 AI requests a day** (environment variable `AI_DAILY_CAP`, default 2000). Then `DAILY_LIMIT_REACHED` and the friendly message in §7.6, until midnight IST.
  - Counters are kept in Firestore so they hold across Cloud Run instances (§8.7).
  - Model call timeouts are set per call (§7.2).
- Headers, set by Firebase Hosting for the app and by the API for its responses:
  - `Content-Security-Policy` with `default-src 'self'`, `script-src 'self'` plus the Google sign-in script host, `connect-src 'self'` plus the Firebase Auth and Firestore endpoints, `frame-src` only for the Firebase auth domain, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, and no `'unsafe-inline'` for scripts. The exact host list is fixed during the build and checked by a test.
  - `Strict-Transport-Security`
  - `X-Content-Type-Options: nosniff`
  - `Referrer-Policy: strict-origin-when-cross-origin` (not `no-referrer`, which would break the referrer restriction on the Firebase API key)
  - a minimal `Permissions-Policy`
- The API accepts same-origin requests only (no CORS); the Hosting rewrite makes it same-origin.
- No user or AI content is ever inserted as HTML. A lint rule bans raw-HTML APIs.
- Quote text and free-text requests are treated as data (§7.2, item 7).
- **Privacy:** the only personal data is the Google account's ID, name and email (held by Firebase Auth) and what users type into their events. No analytics and no tracking cookies. The server doesn't log user text. A short privacy note in the footer says what is stored and where. Account deletion is EM-61 (SHOULD).
- SHOULD: Firebase **App Check** (reCAPTCHA Enterprise) enforced on Firestore and checked on `/api/ai/*`.
- The CI dependency audit fails on high or critical issues.

## 12. Final acceptance test

> A user creates an event, receives a budget and timeline, then returns with changed constraints, such as a lower budget and an event date moved earlier. The application must help them revise the plan; it must not force them to begin again.

**(edited v3) Script.** This runs as E2E with the fixture provider, and as demo D2 against the live AI.

**Setup:** use case Wedding; Jaipur, IN; INR; budget **₹8,00,000**; **150** guests; event date **today + 120 days**. The plan fixture includes a flat venue line, a per-guest catering line that follows the event count, and the task chain *Book venue → Book caterer → Menu tasting*. The user confirms the venue line at **₹2,50,000**.

**Steps:** "return" to the event, in two variants: (a) in the **shared demo account**, the user creates their own event (the pinned demo event is left alone), then reloads the page and comes back to it; (b) a **Google user** signs out, closes the browser context, opens a new one and signs in again. Then open "Change budget, date or guests". Enter budget **"6 lakh"** and move the date **14 days earlier**.

**It passes only if every one of these assertions holds:**

1. After returning, the stored event, lines and tasks are identical to before, in both variants (EM-39, EM-57, EM-58).
2. After the changes are submitted, the before/after view appears, and the stored plan's `version` is unchanged until Apply (EM-52, EM-53).
3. The view shows: budget ₹8,00,000 → ₹6,00,000; a shortfall equal to (Σ line amounts − ₹6,00,000), calculated by code; every not-done task's deadline moved 14 days earlier; every task whose status got worse listed as compressed; and the venue line flagged "Reconfirm for new date".
4. After Apply, the venue line is still ₹2,50,000 and `Confirmed` (EM-42).
5. Σ line amounts + remaining = ₹6,00,000 exactly in minor units, both in the preview and after Apply (EM-44).
6. At least 2 trade-off options are shown, none is selected by default, and no line changes until one is selected and Apply is pressed (EM-54).
7. Discard (in a separate run) leaves the stored plan identical to the snapshot from before the change (EM-53).
8. **(replaces "works for every use case and every currency", which can't be tested)** The test runs for three combinations: wedding with INR and `en-IN`; small celebration with EUR and `de-DE`; community event with JPY and `ja-JP` (JPY has no decimal places).
9. **AI-down variant:** the revision call returns 503. The deterministic revision (new budget, deadlines, shortfall, flags) is still shown and can be applied. The trade-off area shows the error and Retry. The plan is unchanged until Apply (AI-12).

In one line: **build a transparent, personalized, globally usable event-planning SaaS that helps people get events done, not an AI idea generator.**
