## 1. Product definition

Build a **Celebration and Event Planner SaaS** that helps people plan and carry out an event within their budget, preferences, timeline and constraints. The goal is not an AI that suggests party ideas. The goal is an AI that helps users **actually make the event happen**.

**(edited)** The product serves anyone organizing a celebration, anywhere in the world:

- individuals and families
- community organizers
- event professionals running several events

They all use **one planning engine**: event → budget lines → tasks with dependencies → vendor quotes → revisions. What the user selects (EM-05) changes the onboarding questions, the default budget categories and the starting tasks. It does not change the engine. The AI personalizes each plan from the user's own inputs, so two users with the same persona still get different plans (EM-12).

The product manages the connected parts of event planning: budget, guest numbers, venue, decoration, food, vendors, timeline, dependencies and last-minute changes.

## 2. Product principles

These are unchanged from v1:

- Solve real planning problems for clearly defined users, rather than building every possible feature. *(v2 reading: each supported use case must be deep, not shallow. The point is depth, not a limit on who the product serves.)*
- Treat event planning as a connected system: guest count, menu, decoration, budget, vendors and timeline affect one another.
- Use GenAI where it adds real value: understanding needs, personalizing suggestions, adapting to changes, and turning natural language into actionable plans.
- Keep the user in control. The AI should ask, listen and adapt, not assume what the user wants.
- Be open about estimates, assumptions and unverified vendor information.
- Avoid adding features just because they sound impressive.
- Design for change. A revised budget, an earlier date, a changed guest count or a vendor cancellation must update the plan, not force the user to start over.
- Focus on getting the event done (budgets, deadlines, dependencies, coordination, changing requirements), not on inspiration alone.

## 3. Target users and use cases (new)

| Use case (EM-05 selector) | Typical user | What changes in the starting plan |
|---|---|---|
| Tight-budget small celebration | Individual or family: birthday, anniversary, milestone birthday | Fewer categories. Emphasis on trade-offs and doing things yourself. Short planning window |
| Wedding planning | Couple and family | Many vendors. Events with several parts. Long dependency chains |
| Community event coordination | Community or society organizer | Budget pooled from contributions. Permits and logistics tasks. Large, uncertain turnout |
| Multiple events | Event professional | Same engine. The user has many events. There is no client management or billing |

**Global scope:** Users in any country. Each event has **one currency**, chosen when the event is created. Amounts are formatted for the user's locale. Cost estimates take into account the event's location.

## 5. Core user journey

1. The user picks a use case and describes the event: type, location, date, budget and currency, and guest count. **(edited)**
2. The system asks practical onboarding questions, including which parts the event has (for example, a dinner the night before plus the main event).
3. The system generates a personalized starting plan: budget lines, tasks with dependencies and deadlines, and what to ask each vendor.
4. The user refines priorities, budget, guests, theme and requirements.
5. The system keeps a task timeline with dependencies and deadlines.
6. The user records vendor quotes, by pasting text or uploading `.docx` or a text-based PDF, and compares the options. **(edited)**
7. When constraints change, the system shows a **before/after view** of the affected budget lines, tasks and quotes. The user **applies or discards** it. **(edited)**

## 6. Functional acceptance criteria

### 6.1 Event creation and onboarding

| ID | Acceptance criterion |
|---|---|
| EM-01 | **(edited)** The system must let a user create an event by entering the occasion, location (city and country), event date, total budget, currency, expected guest count, and planning window. |
| EM-02 | Before generating a full plan, the system must ask practical clarifying questions such as occasion, budget, expected attendees, event date, desired experience level, spending priorities, and absolute must-haves. |
| EM-03 | The system must generate an initial event plan from the user's actual inputs, not a generic template. |
| EM-04 | The system must support multiple event types, including birthday parties, weddings, 50th-birthday celebrations, and community gatherings. |
| EM-05 | The system must let the user choose a persona or use case, such as a tight-budget small celebration, wedding planning, or community-event coordination. |
| EM-06 | The system must clearly present the generated plan as a starting point the user can refine. |
| EM-37 | **(new)** Each event has exactly one currency, chosen from ISO 4217 currencies. All of the event's amounts are stored and shown in that currency, formatted for the user's locale (for example ₹8,00,000, €8.000, $8,000). |
| EM-38 | **(new)** Amount fields and natural-language input must understand common ways of writing amounts, such as "8 lakh", "1.5 crore", "15k", "€8.000" and "$12,500". The system must show the value it understood before using it. |
| EM-39 | **(new)** Events are saved so the user can leave and return without starting over (needed for the final acceptance test). The MVP saves in the browser and offers export and import as a file. |
| EM-40 | **(new)** A user can create and switch between several events. |

### 6.2 Personalized planning

*EM-07 to EM-12 are unchanged from v1.*

| ID | Acceptance criterion |
|---|---|
| EM-07 | The system must personalize recommendations using the user's preferences, such as atmosphere, guest age groups, interests, cultural preferences, accessibility needs, and venue limitations. |
| EM-08 | The system must let the user refine AI-generated ideas through follow-up conversation. |
| EM-09 | When a user says a suggestion is too expensive or unsuitable, the system must propose relevant alternatives. |
| EM-10 | The system must adapt recommendations for mixed audiences, such as events suited to both children and elderly family members. |
| EM-11 | The system must not assume user preferences. It must ask, listen, and adapt to what the user says. |
| EM-12 | The system must recognize that two users planning the same type of event may need very different plans. |

### 6.3 Budget management

| ID | Acceptance criterion |
|---|---|
| EM-13 | The system must let users organize major expenses into categories such as venue, catering, decoration, photography, and other event costs. |
| EM-14 | The system must help users create an initial budget split across those categories. |
| EM-15 | **(edited)** The system must let users compare planning scenarios. A scenario is a **what-if** (for example, "drop live music" or "cut 30 guests") that shows its effect on budget and timeline next to the current plan and can be **discarded without changing the plan**. |
| EM-16 | When the user gives more money to one category, such as photography, the system must show the effect on the remaining budget. |
| EM-17 | When the guest count rises, the system must identify the costs affected and possible compromises. |
| EM-18 | When expected costs exceed the budget, the system must present trade-offs and let the user choose what matters most, rather than cutting every category automatically. |
| EM-19 | The system must clearly label AI-generated or assumed costs as estimates, not confirmed vendor prices. |
| EM-20 | The system must not present invented prices as confirmed costs. |
| EM-41 | **(new)** Every budget line has a cost label: `AI Estimate` (comes with the assumptions behind it), `Vendor Quoted (Unverified)` (linked to a quote), or `Confirmed` (set only by the user). |
| EM-42 | **(new)** No revision, scenario or AI suggestion may change a `Confirmed` line. If confirmed costs alone exceed a new budget, the system must say so clearly and must not change them. |
| EM-43 | **(new)** Each budget line may have its own **guest count** and a **"scales with guests"** flag. For example, *"Catering – Rehearsal dinner × 40"* and *"Catering – Reception × 200"* are separate lines. When the event's guest count changes, only lines marked as scaling are recalculated, and the change shows in the before/after view. |
| EM-44 | **(new)** Budget totals, remaining budget and allocation percentages are always calculated by code and must add up exactly. They are never written by the AI. |

### 6.4 Timeline and task execution

| ID | Acceptance criterion |
|---|---|
| EM-21 | The system must turn a vague request such as "help me organize my wedding" into a structured sequence of tasks. |
| EM-22 | The system must organize tasks by priority and deadline instead of presenting unrelated checklist items. |
| EM-23 | The system must identify dependencies between tasks. For example, venue and date decisions should come before several later arrangements. |
| EM-24 | **(edited)** When a user marks a task complete, the system must update the plan: tasks that depended on it become available, and progress and "what's next" (EM-26) are recalculated. |
| EM-25 | **(edited)** When a task is late, such as a venue booking, the system must list the tasks that depend on it and are now at risk, along with their new latest-possible dates. |
| EM-26 | The system must show the user what to do next, taking them from "I have an event coming up" to an actionable plan. |
| EM-27 | The system must let the user revise the plan when constraints change, such as a smaller budget or an event date moved two weeks earlier. |
| EM-28 | After a constraint changes, the system must update the affected budget, timeline, dependencies and recommendations without making the user start from scratch. |
| EM-45 | **(new)** Task dependencies must never form a loop. Any change that would create one is rejected with an explanation. |
| EM-46 | **(new)** Each task has a lead time (how long before the event it must be done). Deadlines are calculated backwards from the event date. If the planning window is shorter than a task's lead time, the task is marked compressed or at risk instead of being silently dropped. |
| EM-47 | **(new)** A vendor cancellation is a constraint change. It reopens that vendor's tasks, moves the budget line back to `AI Estimate`, and shows the effect in the before/after view. |

### 6.5 Vendor coordination

| ID | Acceptance criterion |
|---|---|
| EM-29 | The system must help users define what they need from each vendor, such as a caterer, photographer, decorator or venue. |
| EM-30 | The system must help users prepare relevant questions to ask each vendor. |
| EM-31 | **(edited)** The system must let users record vendor quotes by **pasting text**, or uploading a **`.docx`** or **text-based PDF** file. Text is extracted in the browser, so files are not sent to the server. Image scanning (OCR) and legacy `.doc` files are out of scope. |
| EM-32 | The system must compare quotes against the user's budget and requirements. |
| EM-33 | **(edited)** The comparison must show, for each quote: base price, taxes and fees, total, guests covered, what is included, what is excluded or assumed, and items that need clarifying before booking. |
| EM-34 | If the system recommends vendors or mentions availability, it must clearly say the information needs checking. |
| EM-35 | The system must not claim a vendor is available or a price is confirmed unless that has been verified. |
| EM-36 | The system must act as a coordination layer between the user and vendors, not claim that AI can arrange everything automatically. |
| EM-48 | **(new)** If an uploaded file yields too little text (for example a scanned PDF), the system must ask the user to paste the text or upload a text-based file, and must not send it to the AI. |
| EM-49 | **(new)** After extraction, code checks that the quote's **line items add up to its stated total**. Any gap is flagged as a possible hidden or missing charge. |
| EM-50 | **(new)** If a quote's currency is different from the event's currency, it is flagged, and the user enters the converted amount. The system does not convert currencies. |
| EM-51 | **(new)** Each quote records whether its prices include or exclude tax. If the quote doesn't say, the item is marked "tax treatment unclear" and added to the questions to ask the vendor. |

### 6.6 Plan revision and scenarios (new)

| ID | Acceptance criterion |
|---|---|
| EM-52 | **(new)** Every constraint change (budget, date, guest count, vendor cancellation, or a request in plain language) produces a **proposed revision**, shown as a before/after view of the affected budget lines, task deadlines, dependencies and quotes. |
| EM-53 | **(new)** A proposed revision changes nothing until the user selects **Apply**. **Discard** leaves the plan exactly as it was. |
| EM-54 | **(new)** When a revision leaves a shortfall, it offers at least two trade-off options with their effects (EM-18). The user picks one; the system never chooses on its own. |

## 8. Architecture principles (new)

### 8.1 Who does what

| GenAI does | Code does |
|---|---|
| Understanding the event description and natural-language requests | All money arithmetic: totals, remaining budget, per-guest scaling, rounding |
| Writing onboarding questions that fit the context (AI-01) | Turning the AI's relative category weights into amounts that add up exactly |
| Proposing categories, tasks, lead times and dependencies for the use case and location | Calculating dates backwards from the event, checking for dependency loops, flagging compressed tasks |
| Estimating cost ranges for the location and currency, with stated assumptions | Protecting `Confirmed` lines, and calculating before/after differences |
| Pulling structured fields out of quote text | Checking that quote line items add up, and flagging currency mismatches |
| Explaining trade-offs and suggesting alternatives | Checking AI output against the data format, and enforcing Apply/Discard |

**Rule:** the AI returns structured **proposals**. Code checks them and calculates the result. The user approves. The AI never writes final amounts or dates into the plan.

### 8.2 Where cost estimates come from

The AI estimates costs from the user's inputs: location, currency, guest count, budget level and use case. Each estimate is a range with its assumptions stated, and is labelled `AI Estimate` (EM-41). There is no built-in price table, which keeps the product global and avoids AI-07's ban on dummy data. Users replace estimates with quotes as they collect them.

### 8.3 Where task lead times come from

The AI proposes each task's lead time and dependencies for the use case. Code keeps each lead time within sensible limits, rejects dependency loops, and calculates the deadlines (EM-46).

### 8.4 Reading quote files

`.docx` is read with mammoth and text PDFs with pdfjs-dist, both in the browser. Only the extracted text goes to the server and then to the AI, which returns the fields in a defined format. The scanned-file check (EM-48) and the line-item total check (EM-49) run in code.

## 11. MVP scope

**Must have**

- Choosing a use case and onboarding questions (EM-01 to EM-06, EM-37, EM-38)
- A personalized starting plan: budget lines with per-line guest counts, and tasks with dependencies and backward-calculated deadlines
- Cost labels, and protection of confirmed costs (EM-41, EM-42)
- Before/after revision with Apply and Discard (EM-52 to EM-54). **This is the final acceptance test.**
- Quote comparison from pasted text and `.docx`, including the total check and the currency and tax flags (EM-31, EM-33, EM-48 to EM-51)
- Saving in the browser and multiple events (EM-39, EM-40)
- Assumptions panel, WCAG AA, tests, security measures, deployment, and the requirements table in the README

**Should have**

- Text-based PDF upload
- What-if scenarios you can discard (EM-15)
- Updates when a task is completed or late (EM-24, EM-25)
- Vendor cancellation (EM-47)

**Won't have in the MVP**

- Logins, and sharing with Edit or View roles (deferred; the plan can still be exported)
- Converting between currencies
- OCR and legacy `.doc` files
- Full sub-events (per-line guest counts are used instead)
- Live vendor marketplace, real-time availability or confirmed pricing
- Invitations, reminders, and guest RSVP management

## 12. Final acceptance test

> A user creates an event, receives a budget and timeline, then returns with changed constraints, such as a lower budget and an event date moved earlier. The application must help them revise the plan; it must not force them to begin again.

**It passes only if all of these are true (new):**

1. The event, budget and timeline are still there when the user returns (EM-39).
2. Entering the new budget and date produces a proposed revision. Nothing changes until the user selects Apply (EM-52, EM-53).
3. The before/after view shows which budget lines changed, which deadlines were compressed or are now at risk, and which quotes are affected.
4. `Confirmed` lines are unchanged. If they exceed the new budget, the user is told (EM-42).
5. The revised budget adds up exactly to the new total (EM-44).
6. Any shortfall is presented as trade-off options for the user to choose from, not as automatic cuts (EM-18, EM-54).
7. Discard restores the plan exactly as it was.
8. This works for every use case and every currency, using whatever the user enters.

In one line: **build a transparent, personalized, globally usable event-planning SaaS that helps people get events done, not an AI idea generator.**
