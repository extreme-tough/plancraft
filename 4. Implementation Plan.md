# PlanCraft MVP: implementation plan (due 1 Nov 2026, 11:59 PM IST)

## Context

The repo has only specs today: `3. Product-specification-v3-mvp.md` (the source of truth), `DESIGN.md` (tokens), and a Figma file "PlanCraft" with 4 screens, each in a desktop and a mobile frame. This plan turns them into a working, deployed MVP that scores on the six PromptWars categories.

Decisions from the founder's answers, which this plan follows:

| Decision | Answer |
|---|---|
| Stack | **Next.js on Google**: Firebase App Hosting (Cloud Run), Firebase Auth, Firestore, Vertex AI Gemini, Cloud Scheduler. No SQL or ORM. The "schema" is Zod-typed Firestore documents |
| Guest model | **Spec v3**: `pricing` (flat or per guest) + `guestSource` (event or own). No `scales_with_guests` flag |
| Figma Revision "Option B: headcount 200 → 175" | **Keep the spec rule.** AI options can't change event budget, date or guests. Option B's copy changes to a line-level trade-off; a headcount change stays in the constraint form |
| Figma extras (fit score, payment status, moodboard, team notes, notifications) | **All kept**, tiered as SHOULD after the MUSTs. The fit score is **calculated by code** and labelled "Best fit by our checks", never "AI pick" |

Today is Sat 24 Oct. There are about 7.5 working days. The estimates below add up to slightly more than that, so the order of cuts in §6 matters.

                              before: z.string(), after: z.string() })).max(3),

**Calculated, never stored:** remaining, percentages, deadlines and latest starts, schedule status (on track / tight / overdue), at-risk tasks, quote totals and checks, the fit score (EM-68), notifications (EM-65), "Next up".

**New requirements to add to the spec (Figma extras, all SHOULD):**
- **EM-64:** Payment status per line: amount paid and balance due date. A due date adds a calculated alert.
- **EM-65:** Notifications bell, built **only** from calculated alerts (overdue or tight tasks, confirmed-cost overrun, balance due within 7 days, quote flags), each dismissible. No push or email.
- **EM-66:** Team notes per event and per quote. Plain text.
- **EM-67:** Moodboard: up to 6 user-uploaded images (JPEG, PNG or WebP, under 1 MB each, required alt text). Stored in Cloud Storage under the owner's path.
- **EM-68:** Quote fit score, 0–100, calculated by code: 50 for budget fit, 30 for needs coverage, 20 minus deductions for total gaps, unclear tax and unverified values. The parts are shown. The badge says "Best fit by our checks", the user still links and confirms, and AI-09 and EM-34 stay intact.

**How dependency loops are prevented (EM-45)**, in four layers:
1. `src/domain/graph.ts` exports `findCycle(tasks): string[] | null` (Kahn's algorithm with DFS path recovery), called by `planInvariants` on every Zod parse.
2. Every input path rejects loops: AI plan output (rule P4), revision options (R5, the option is dropped), user dependency edits (refused with the loop named, e.g. "A → B → A"), and imports.
3. The dependency picker in the task editor greys out tasks that depend on the current one, so a loop can't be picked in the first place.
4. Property test INV-3 checks that no sequence of accepted operations produces a loop.

Firestore rules can't walk a graph, so the server re-parses with `EventPlan` whenever it reads a plan for `/api/ai/revise`. A corrupt plan returns 409.

## 4. AI integration

All three calls share `src/server/ai/pipeline.ts`:

1. Verify the Firebase ID token.
2. Check the rate limits: per user ID, or per IP for `demo-shared`, plus the daily cap of 2,000.
3. Check the request with Zod.
4. Build the prompt. Untrusted text goes inside `<quote>` / `<request>` delimiters.
5. Call `generateContent` with `responseMimeType: 'application/json'` and `responseJsonSchema: z.toJSONSchema(Output)`, with a timeout (45 s for the plan, 30 s for the others).
6. `JSON.parse`, then Zod `safeParse`, then the rule functions.
7. On failure, make **one repair attempt** that sends the failed rule IDs.
8. Return the envelope `{ ok, data | error: { code, message, retryable } }`.

Logs hold rule IDs only, never user text. The provider is behind an interface, `AiProvider`. `FixtureProvider` is selected by `AI_PROVIDER=fixture`, and the app **refuses to boot** with it when `NODE_ENV=production` (AI-05).

| Feature | Endpoint | Model | Output schema (Zod mirrors spec §7.3–7.5 exactly) | Extra rules | Fallback (§7.6) |
|---|---|---|---|---|---|
| Plan generation | `POST /api/ai/plan` | `GEMINI_MODEL` (Flash), temperature 0.4, max output 8k tokens | `PlanResponse`: summary, 3–25 `budgetLines` {key `L\d{1,2}`, category, name, part, pricing, weight (0,100], estimateLow/High, assumptions 1–3, vendorNeeds ≤5, vendorQuestions ≤5}, 5–40 `tasks` {key `T\d{1,2}`, title, line, priority, leadTimeDays 0–540, durationDays 1–90, dependsOn ≤5}, assumptions 1–10, openQuestions ≤5 | P1–P8 (unique keys, refs resolve, no loops, parts match, high ≥ low, at most one contingency, a priority category present) | Event saved. "Retry" or "Start with an empty plan" (categories only, no invented amounts) |
| Revision proposal | `POST /api/ai/revise` (the server loads the plan from Firestore for the token's user ID) | Same, temperature 0.3, 4k tokens | `RevisionResponse`: interpretation, constraintChanges ≤3 (shown back for the user to confirm, **never applied**), options ≤3 {key O1–O3, title, rationale, ops 1–12 {op ∈ set_amount, set_unit_cost, set_guests (own-count lines only), remove_line, add_line, remove_task, add_task, set_lead_time; target; value; newLine; newTask}, assumptions}, assumptions | R1–R8. Invalid options are dropped individually. At least 2 must remain when shortfall > 0 | The deterministic revision is still shown and can be applied. Trade-off area shows Retry or "Edit lines yourself" |
| Quote extraction | `POST /api/ai/quote` | Same, temperature 0, 4k tokens | `QuoteResponse`: vendorName, currency, items ≤50 {description, kind item/fee/tax/discount, quantity, unitPrice, amount}, statedTotal, taxTreatment, guestsCovered, inclusions, exclusions, needsCoverage (one per input need), clarifications, validUntil | Q1–Q2 fail the response. Q3–Q5 flag values ("Check: not found in quote text", via digit-string grounding) | Raw text saved. Retry or "Enter details manually" (same fields; EM-49 to EM-51 checks still run) |

The Zod files are `src/server/ai/schemas/{plan,revision,quote}.ts`. Each exports `Request`, `Response` and `rules: Array<(data, ctx) => RuleFailure | null>`. The provider schema is generated from the same Zod object, so the TypeScript types, runtime check and model contract can't drift apart. Gemini's schema subset means no `oneOf` (the ops are flat, with nullable fields).

**How Confirmed costs are protected (EM-42):**
1. Lines are sent to the model with `locked: true`, and the prompt says locked lines must not be targeted.
2. Rule R4 drops any option that targets a locked line.
3. The **AI schemas have no `label` field and no event-level ops**, so the model can't express those changes at all.
4. `applyProposal()` in `src/domain/proposal.ts` takes a snapshot of the confirmed lines first and throws (aborting the whole Apply, INV-10) if any differs afterwards.
5. Property test INV-2 runs random proposals and AI options against random plans.
6. Deterministic recalculations (a guest change) skip confirmed lines and add an "Confirmed for N guests" warning instead.
7. A date change flags confirmed lines "Reconfirm for new date" without touching their amounts.
